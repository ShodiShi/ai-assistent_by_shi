# Этап 1 — Jarvis.Core в текстовом режиме

Дата: 2026-09-29
Родительский документ: `2026-09-29-jarvis-roadmap.md`
Статус: согласовано с пользователем в чате, ожидает финального review этого документа.

## Цель этапа

Рабочее ядро `Jarvis.Core` без аудио: ввод команд с клавиатуры, разбор уровнями 1-2, выполнение
через небольшой набор реальных инструментов Windows, текстовый ответ в консоль (озвучка
подставляется как печать — реальный TTS появится в Этапе 2). Это фундамент, на котором Этапы 2-5
достраивают аудио, IPC с Guard, игровой режим и LLM-уровень, не меняя интерфейсы уровня 1.

## Вне рамок этапа

Аудио (NAudio/VAD/Whisper/TTS), Guard/IPC, игровой режим, уровни 3-4 разбора команд (LLM и
уточнение), окно настроек, автозапуск, wake word. Эти интерфейсы (`ICommandResolver` для
уровня 3, `ILlmProvider`) закладываются как расширяемые точки, но не реализуются.

## Компоненты

- **`Jarvis.Core.Config`** — загрузка и валидация `config.yaml`, `apps.yaml`, `games.yaml`
  (пока не используется, но парсится, чтобы формат был готов к Этапу 4),
  `intents/*.yaml`, `user_aliases.yaml` (создаётся пустым, если отсутствует). YamlDotNet.
- **`Jarvis.Core.Nlu`**
  - `ICommandResolver` — общий интерфейс `Task<ResolveResult> Resolve(string utterance, NluContext ctx)`.
  - `RuleBasedResolver` (уровень 1) — регэкспы + словарь алиасов из `apps.yaml`/`config.yaml`,
    простая лемматизация (окончания прилагательных/глаголов для основных команд), разбор чисел
    словами («пять», «двадцать процентов») и времени («на пять минут»).
  - `EmbeddingResolver` (уровень 2) — ONNX Runtime + `multilingual-e5-small` (int8), сравнение
    косинусным сходством с образцами из `intents/*.yaml`, извлечение параметров теми же
    правилами, что и уровень 1, порог сходства из `config.yaml`.
  - `CommandPipeline` — последовательно опрашивает резолверы по порядку, останавливается на
    первом уверенном результате; если ни один не уверен — `UnresolvedResult` (в этом этапе просто
    печатается «не понял», реальный уровень 4 — в Этапе 5).
- **`Jarvis.Core.Tools`** — `ITool` (`string Name`, `JsonSchema ArgsSchema`,
  `Task<ToolResult> ExecuteAsync(JsonElement args, ToolContext ctx)`), реестр `IToolRegistry`,
  резолвится через DI.
- **`Jarvis.Core.Logging`** — Serilog с ротацией по дням, поля: время, фраза, уровень разбора,
  инструмент, результат (без аудио, срок хранения — из `config.yaml`).
- **`Program.cs`** (консольный host, `Microsoft.Extensions.Hosting`) — DI-контейнер, цикл
  `Console.ReadLine()` → `CommandPipeline.Resolve` → `ITool.ExecuteAsync` → печать ответа.

## Инструменты этапа 1

1. **`open_app(name)`** — поиск в `apps.yaml` по имени/алиасу (регистронезависимо), запуск через
   `Process.Start`; если не найдено — короткий ответ с просьбой уточнить (полноценный поиск по
   Пуск/`shell:AppsFolder` — Этап 5).
2. **`close_app(name)`** — мягкое закрытие через `Process.CloseMainWindow()` для всех процессов с
   подходящим именем; принудительное завершение (`Process.Kill()`) только после отдельного
   текстового подтверждения «да» на следующем вводе.
3. **`system_control(action: shutdown|restart|sleep|lock)`** — `lock` сразу
   (`LockWorkStation` из `user32.dll`); `shutdown`/`restart` — только после подтверждения «да»,
   запуск через `shutdown /s /t 20` (или `/r`) с таймером 20 c и возможностью отменить командой
   «отмена» → `shutdown /a`; `sleep` — `SetSuspendState` после подтверждения (обратимо, но всё
   равно спрашиваем, т.к. действие ощутимо для пользователя).
4. **`volume_control(action: up|down|mute|unmute, amount?)`** — через NAudio CoreAudio API
   (`MMDeviceEnumerator`), шаг по умолчанию из `config.yaml`.
5. **`get_system_info()`** — батарея (`System.Windows.Forms.SystemInformation.PowerStatus` или
   WMI `Win32_Battery`), CPU/RAM (`PerformanceCounter`/WMI), свободное место на диске
   (`DriveInfo`) — короткая текстовая сводка.

Все инструменты и их аргументы описаны JSON-схемой, которую `CommandPipeline` использует для
валидации параметров, извлечённых уровнями 1-2, до вызова `ExecuteAsync`.

## Поток данных

```
Console.ReadLine()
  → CommandPipeline.Resolve(text)
      → RuleBasedResolver (level 1)     [десятки мс]
      → EmbeddingResolver (level 2)     [десятки-сотни мс, включая инференс ONNX]
  → ResolveResult { ToolName, Args, Confidence, Level }
  → JSON Schema validation аргументов
  → ITool.ExecuteAsync
  → ToolResult { Success, Message }
  → Serilog: время, фраза, уровень, инструмент, результат
  → печать ToolResult.Message в консоль
```

## Обработка ошибок

- Конфиг не найден/невалиден → внятное сообщение при старте, использовать значения по умолчанию
  там, где это безопасно (список инструментов не зависит от `apps.yaml`).
- ONNX-модель уровня 2 не найдена → предупреждение в лог, `EmbeddingResolver` пропускается,
  работают только правила уровня 1 (деградация, а не падение процесса).
- Инструмент бросает исключение → перехватывается в `CommandPipeline`, логируется, пользователю —
  «не получилось выполнить команду», процесс не падает.
- `close_app`/`system_control` без ожидаемого подтверждения в следующей реплике → действие не
  выполняется, тайм-аут подтверждения (например, 15 c условного «времени») сбрасывает ожидание.

## Тестирование

`Jarvis.Core.Tests` (xUnit):
- Юнит-тесты `RuleBasedResolver` и `EmbeddingResolver` по отдельности (мокнутый `IToolRegistry`).
- Набор из **50+ тестовых фраз** на русском (`Resources/test-phrases.yaml`), покрывающий все 5
  инструментов, включая:
  - точные формулировки («открой хром», «выключи ноут», «сделай громче»);
  - вариативные/разговорные («глянь что там с батарейкой», «вырубай комп», «прибавь звука
    процентов на 20») — должны закрываться уровнем 2, если не попали в regex уровня 1;
  - неоднозначные/незнакомые фразы → ожидаемый результат `Unresolved`, а не случайный инструмент;
  - фразы с числами и временем («громкость на 30», «закрой телеграм через подтверждение да/нет»).
- Тест на валидацию аргументов: инструмент не вызывается, если схема не проходит.
- Отчёт по итогам прогона: доля команд, закрытых уровнем 1 / уровнем 2 / нерешённых —
  ориентир на достижение 70-80% суммарно уровнями 1-2, зафиксированный в roadmap.

## Конфигурация (черновой формат для Этапа 1)

`config.yaml`: язык (`ru`), пороги уровня 2 (`embedding_threshold`), шаг громкости, таймер
подтверждения shutdown, срок хранения логов.
`apps.yaml`: список `{ name, aliases[], path|shell_command }` (хром, телеграм, дискорд, VS Code,
проводник и т.д. — начальный набор на 6-8 приложений, установленных на машине пользователя).
`intents/*.yaml`: по файлу на инструмент, 10-20 примерных формулировок каждый.

## Ручной чек-лист приёмки этапа

1. `dotnet run --project src/Jarvis.Core` стартует без ошибок при валидных конфигах.
2. Фразы «открой хром» / «закрой хром» реально открывают/закрывают браузер.
3. «выключи ноут» требует подтверждения, «отмена» останавливает таймер выключения, реального
   выключения без слова «да» не происходит.
4. «сделай громче» / «тише» / «без звука» меняют системную громкость (проверить микшером
   Windows).
5. «как там батарея» / «сколько памяти свободно» возвращает осмысленную сводку.
6. Фраза-мусор («расскажи анекдот про кота») не вызывает случайный инструмент, а даёт понятный
   ответ о том, что команда не распознана.
7. `dotnet test` — все тесты зелёные, отчёт показывает ≥70% фраз, закрытых уровнями 1-2.
8. Лог-файл в `logs/` содержит по строке на каждую введённую команду с нужными полями, без
   записи самого аудио (в этом этапе аудио и так нет).

После прохождения чек-листа — commit, review, переход к implementation-плану Этапа 2.
